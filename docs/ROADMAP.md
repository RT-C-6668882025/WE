# WE 开发待办

基线：v0.6.1。本文把需求、候选组件与实际接入状态分开记录；勾选须有完整用户流程验证。

## P0：基本交互与画布

- [ ] **撤回上次**：撤销当前输入/画布的最近一次编辑操作。画笔、橡皮、选区变换、图层编辑应进入统一操作历史，不仅是删除最后一条笔迹。
- [ ] **全部撤回**：一键移除当前输入/当前画布的全部笔迹；不删除工作区、历史对话、PDF 原件、其他画作。将此操作记为一个可恢复的历史项。
- [ ] 两种操作在首页手写和绘画界面均有明确入口；按钮状态与可撤回状态一致。
- [ ] **首页显式“＋新建”**：创建新任务/工作区；保存旧任务草稿后切换，不靠长按角落或深层菜单发现。
- [ ] **绘画显式“＋新建”**：同一工作区内创建独立画作；保留旧画作，并能从作品列表重新打开。当前深层菜单已有动作，显式按钮与画作列表尚未完成。
- [ ] **真正无限画布**：绘画文档采用无分页世界坐标，支持向四个方向移动和书写；独立保存视口。固定 PDF 页面继续负责 PDF 批注。
- [ ] 无限画布采用稀疏空间索引、视口裁剪与分块/几何缓存，避免按一张巨型位图分配内存。
- [ ] 存储、选区、图层、擦除、撤回、导出和 MCP 截图使用同一世界坐标；导出/读取必须指定选区、视口或内容边界。
- [ ] 完成从入口到恢复的设备测试：新建→书写→平移到远处/负坐标→继续写→撤回上次→全部撤回→恢复→退出重开→导出/Agent 读取。

参考已检查的 xnotes 源码（26f42b2945df85087ab8d36a5344aa0e0c949707）：
`core/infinite/InfiniteDocument.kt`、`CanvasViewport.kt`、`SpatialIndex.kt`、
`core/history/History.kt`、`gl/InfiniteCanvasView.kt`。
其关键设计是文档、视口、空间索引、操作历史与渲染分离；WE 当前 PaperPage/LayerRenderer 仍依赖固定 PDF 页面，不能把调大 page.width/height 作为完成。

## P1：MCP 接入准备

当前工具与连接状态见 [MCP 能力与待补接口](../mcp/capabilities.md)。已有 Android 本机服务与独立中继源码，公网实际部署/客户端端到端连接仍需验证。

- [ ] 当前状态：返回当前工作区、编辑器、文档/画布、页码、选区与 revision。
- [ ] 首页手写：一次获取当前草稿的真实笔迹、图像、坐标和版本；不依赖 Agent 手动查 JSON 文件。
- [ ] 画布资源：列出/新建/读取画作；无限画布按世界坐标视口或选区读取。
- [ ] 结构化编辑：通过原子操作批次新增/修改文字、形状、图层与批注；使用 expected_revision 与 operation_id。
- [ ] 提交与事件：明确用户何时发送；提供变更游标/订阅读取设计，避免不断重复读取整个工作区。
- [ ] 输出与版本：交付文件、学习页、图解及反馈，保留原件与可回退版本；明确哪个对象是交付结果。
- [ ] 独立 HTTPS 中继部署、手机配对、实际目标 MCP 客户端兼容、断线重连及后台可用性验证。
- [ ] 完整闭环：手写需求→Agent 读当前任务与选区→生成/批改→工作区出现结果→用户继续写→Agent 读增量。

## 次序

先明确用户输入/文档/操作历史契约及显式入口，再接当前状态与手写读取；无限画布接口随其世界坐标模型一同完成，避免让 MCP 固化当前 PDF 画布的限制。
